# 本地视频放大部署手册（Video2X / FlashVSR / SeedVR2）

> 本文件属于 [video-upscale-deploy](../README.md) 仓库。项目简介、安装顺序速览见 [README](../README.md)，
> 技术栈版本与关键坑见 [AGENTS.md](../AGENTS.md)，架构与问题记录见 [DEVELOPMENT.md](../DEVELOPMENT.md)。

面向 RTX 4070 Super 12G、4070 Ti Super 16G、4090 24G 三张卡的完整可执行方案。
全部脚本为 PowerShell，双击或命令行运行即可，不需要写代码。

> 本版已按各项目官方源码逐项核对并修正。所有参数名、模型文件名、缩放倍数限制
> 都以官方代码为准，核对结果见文末「八、本次修订记录」。

## 一、先搞清楚：三套方案各自是什么

| | 方案一 Video2X | 方案二 FlashVSR | 方案三 SeedVR2 |
|---|---|---|---|
| 技术路线 | 逐帧超分（Real-CUGAN / Real-ESRGAN）+ 补帧 | 流式扩散超分（Wan2.1 底模） | 一步扩散视频修复（ByteDance） |
| 依赖 | C++/Vulkan 便携包，**不装 Python、不用 CUDA** | ComfyUI + 自定义节点 | ComfyUI + 自定义节点（自带 CLI） |
| 画质 | 一般，锐化感明显 | 好，时序稳定不闪烁 | 最好，接近"重拍"效果 |
| 速度（参考量级） | 最快，逐帧线性增长，分钟级 | 扩散类里最快；官方口径单张 A100 上 768×1408 约 17 FPS，一段 10 分钟素材约十几分钟 | 最慢，数小时级 |
| 显存 | 很低（Vulkan 推理，通常 2 GB 以内） | 6–16 GB 可调 | 3B FP8 权重约 3.4 GB，7B FP16 权重约 16.5 GB（另需激活与缓存） |
| 适合场景 | 批量出草稿、番剧、老片快速放大 | 真人短视频、直播切片精修 | 关键镜头、成片交付 |
| 批量能力 | 官方 CLI，脚本循环即可 | 走 ComfyUI HTTP API，脚本循环 | **自带 CLI，天生为批量设计** |

**结论：三个都装，但按用途分工。**
日常批量用方案一，正式出片用方案三，方案二在"比方案一好、比方案三快"的位置上做补位。

## 二、三张卡怎么分配

| 显卡 | 显存 | 推荐主力 | 具体配置 |
|---|---|---|---|
| RTX 4070 Super | 12 GB | 方案一 + 方案二 | 方案一 Real-CUGAN 2x；方案二 `-Mode tiny-long`（长视频省显存）；方案三用 `-Profile 12g`（3B FP8 + BlockSwap 24） |
| RTX 4070 Ti Super | 16 GB | 方案二 + 方案三 | 方案二 `-Mode tiny`；方案三 `-Profile 16g`（3B FP16 + BlockSwap 16） |
| RTX 4090 | 24 GB | 方案三 | `-Profile 24g`（7B FP8 mixed + torch.compile），方案二可开 `-Mode full` 冲画质 |

**多卡叠加**：SeedVR2 的 `--cuda_device` 支持逗号分隔（如 `0,1`），可让 4090 + 4070TiS
同时跑一个长视频。每张卡各自加载一份模型，所以显存需求不叠加，是各自独立；
提速幅度取决于两张卡的速度差，不会正好翻倍。

## 三、目录与路径约定

程序与模型放 SSD，素材与成品放机械盘，读写特性能对上。默认约定写在 `common.ps1`：

```
C:\AI\                        <- 程序 + 模型（改 UPSCALE_ROOT 可换）
  ComfyUI\                    <- 方案二、三共用的底座
    .venv\                    <- 独立 Python 环境，不污染系统 Python
    custom_nodes\             <- 各方案的自定义节点
    models\
      FlashVSR-v1.1\          <- 方案二权重（约 7.0 GB）
      SEEDVR2\                <- 方案三权重（按档位 3.9–42.4 GB）
  Video2X\                    <- 方案一便携包

E:\VideoUpscale\              <- 素材与成品（改 UPSCALE_IO 可换）
  input\                      <- 待放大的视频丢这里
  output\                     <- 成品出这里
```

> 只改 `common.ps1` 顶部两个变量，所有脚本自动跟着走，不用逐个改。

### 第 1 步：方案一 —— Video2X（最快见效）

```powershell
powershell -ExecutionPolicy Bypass -File .\01-Video2X\安装Video2X.ps1
```

脚本内部 4 步，各自作用：

| 步骤 | 作用 |
|---|---|
| 1 检查环境 | 确认有可用显卡，建立输出目录 |
| 2 查最新发行版 | 用 GitHub API 拿最新 tag 和 Windows 压缩包地址（资产名固定为 `video2x-windows-amd64.zip`，不带版本号），避免写死版本号 |
| 3 下载并解压 | 落到 `C:\AI\Video2X`，缓存到临时目录，重跑不重复下载 |
| 4 定位 exe 并自检 | 跑 `--version` 和 `--list-devices`，确认能识别到你的显卡 |

**图形界面**（装完就能用，推荐新手）：

```powershell
powershell -File .\01-Video2X\Video2X_GUI.ps1
```

深色主题界面，窗口里可以选文件/目录、选处理器和模型、拖滑块调画质、点按钮就开始。支持 Real-CUGAN / Real-ESRGAN / Anime4K / RIFE 四种模式，模型和倍数会自动联动校验。底部日志面板实时显示 video2x 输出，方便排错。

命令行批量放大：

```powershell
# 通用/真人素材，2 倍，最快
powershell -File .\01-Video2X\批量放大.ps1 -InputPath "E:\VideoUpscale\input" -Scale 2

# 细节更多，Real-ESRGAN 4 倍
powershell -File .\01-Video2X\批量放大.ps1 -InputPath "E:\VideoUpscale\input" -Processor realesrgan -Scale 4 -Model realesrgan-plus

# 番剧：Anime4K 着色器，几乎不耗时
powershell -File .\01-Video2X\批量放大.ps1 -InputPath "a.mp4" -Processor libplacebo -Width 3840 -Height 2160

# 只补帧：24fps -> 60fps
powershell -File .\01-Video2X\批量放大.ps1 -InputPath "a.mp4" -Processor rife -FrameMul 3
```

批量脚本的作用：**逐个文件调用 video2x 命令行，自动跳过已完成、参数非法提前报错、输出统一命名**。
参数合法性检查放在最前面，避免跑到一半才失败。

**模型与倍数的对应关系**（这是最容易踩坑的地方，Video2X 不是所有模型都支持所有倍数）：

| 处理器 | 模型 | 支持的倍数 |
|---|---|---|
| realcugan | `models-se` | 2 / 3 / 4 |
| realcugan | `models-pro` | 2 / 3（**没有 4 倍**） |
| realcugan | `models-nose` | 仅 2 |
| realesrgan | `realesr-animevideov3` | 2 / 3 / 4 |
| realesrgan | `realesrgan-plus` | 仅 4 |
| realesrgan | `realesrgan-plus-anime` | 仅 4 |
| rife | 见 `-Model` 白名单 | 只做补帧，用 `-FrameMul` 控制倍数 |

**RTX 4070 SUPER 实测速度**（360p 源，CRF 17，preset slow）：

| 处理器 | 模型 | 操作 | 输出分辨率 | 速度 | 10 分钟视频预计耗时 |
|---|---|---|---|---|---|
| realcugan | models-se | 2x 放大 | 720p | ~33 FPS | ~15 分钟 |
| realesrgan | realesr-animevideov3 | 4x 放大 | 1440p | ~27 FPS | ~37 分钟 |
| libplacebo | anime4k-v4-a+a | 2x 放大 | 720p | ~100 FPS | ~5 分钟 |
| rife | rife-v4.6 | 2x 补帧 | 同源（60fps） | ~298 FPS | ~1.7 分钟 |

> 实测环境：RTX 4070 SUPER 12G，驱动 616.36，Video2X 6.4.0（Vulkan）。
> 速度为纯推理+编码合计，编码用 libx264 slow / CRF 17，若换 fast / CRF 23 还能更快。
> Video2X 6.4.0 Windows 版有时处理成功但退出码非 0（Vulkan 清理阶段的小问题），文件实际正常，批量脚本已做兼容处理。

### 第 3 步：方案二 —— ComfyUI + FlashVSR

```powershell
powershell -ExecutionPolicy Bypass -File .\02-FlashVSR\安装FlashVSR.ps1
# 想同时装老版 v1 做对比：加 -AlsoLegacyV1
```

| 步骤 | 作用 |
|---|---|
| 1 检查环境 | 确认底座就绪、磁盘余量 ≥ 15 GB |
| 2 装 VideoHelperSuite | 提供"读视频成帧序列 / 帧序列写回视频"的节点，FlashVSR 本身只管帧 |
| 3 装 FlashVSR 节点 | 克隆 Ultra-Fast 节点，并确认 `triton-windows` 和 `posi_prompt.pth` 就位 |
| 4 下载权重 | 从 HuggingFace 镜像拉 `FlashVSR-v1.1` 到 `models\FlashVSR-v1.1` |
| 5 校验权重 | 逐个核对 4 个关键文件是否齐全，缺了立刻报错 |
| 6 冒烟测试 | 跑 ComfyUI 的 `--quick-test-for-ci`，让它真正加载一遍自定义节点 |

权重清单（合计约 7 GB）：

```
diffusion_pytorch_model_streaming_dmd.safetensors   5.68 GB   主模型
LQ_proj_in.ckpt                                     0.58 GB   低质输入投影
Wan2.1_VAE.pth                                      0.51 GB   VAE
TCDecoder.ckpt                                      0.19 GB   时序解码器
```

> 四个文件合计 6.95 GB，口径同上（1 GB = 10⁹ 字节）。

> **注意**：节点还依赖一个 `posi_prompt.pth`（约 4 MB），它**不在** HuggingFace 权重里，
> 而是随节点仓库一起提交，由 `nodes.py` 从节点目录自身加载。所以这个节点必须用
> `git clone` 装（脚本就是这么做的），别用不完整的 zip 包，否则会报文件不存在。

**批量放大（命令行，不用开网页）**：

```powershell
# 4090：4 倍
powershell -File .\02-FlashVSR\批量放大.ps1 -InputPath "E:\VideoUpscale\input" -Scale 4

# 4070S 12G：长视频省显存
powershell -File .\02-FlashVSR\批量放大.ps1 -InputPath "a.mp4" -Mode tiny-long -Scale 4

# 追求画质（吃显存）
powershell -File .\02-FlashVSR\批量放大.ps1 -InputPath "a.mp4" -Mode full -Scale 4

# 服务没开，让脚本自己拉起来
powershell -File .\02-FlashVSR\批量放大.ps1 -InputPath "E:\VideoUpscale\input" -AutoStart

# 用显卡编码器出片
powershell -File .\02-FlashVSR\批量放大.ps1 -InputPath "a.mp4" -Format video/nvenc_h264-mp4 -Bitrate 20
```

**原理**：ComfyUI 本身是 HTTP 服务。脚本把工作流以 API 格式 POST 给 `/prompt`，
轮询 `/history` 等它跑完，再把成品从 ComfyUI 输出目录搬到 `E:\VideoUpscale\output`。
这样就能像方案一一样"丢一个文件夹进去、出来一批成品"。

**关键参数含义**：

| 参数 | 作用 |
|---|---|
| `-Mode tiny / tiny-long / full` | tiny 默认更快；tiny-long 显著降低长视频显存；full 画质最高 |
| `-Scale 2 / 3 / 4` | 节点只接受 2–4；4 倍效果总是更好，显存不够时用 2 |
| `-NoTiledDit` | 关掉 DiT 分块，省时间但吃显存（24G 可以关） |
| `-NoTiledVae` | 关掉解码分块，同上 |
| `-UnloadDit` | 解码前先卸下 DiT，压低显存峰值，代价是慢 |
| `-Format` | 四选一：`video/h264-mp4`、`video/h265-mp4`、`video/nvenc_h264-mp4`、`video/nvenc_hevc-mp4` |
| `-Crf` | **只对 CPU 编码器（h264/h265-mp4）有效**，脚本默认 17（节点自身默认 19；数值越小质量越高） |
| `-Bitrate` | **只对 nvenc 格式有效**，单位 Mbps，默认 10 |

> **编码质量参数不能混用**：VideoHelperSuite 的格式定义里，`h264-mp4`/`h265-mp4` 用 `crf`，
> 而 `nvenc_h264-mp4`/`nvenc_hevc-mp4` 用的是 `bitrate` + `megabit`，没有 `crf` 这个输入。
> 给 nvenc 传 crf 不会报错但会被静默忽略，质量会锁死在默认码率上。脚本已按格式自动分派。

> **长视频内存**：这个工作流会把整片读成帧序列放进内存（`frame_load_cap = 0` 表示全片）。
> 1080p 一小时约 30 万帧，内存扛不住。超长素材建议先切段，或用方案三的 `-ChunkSize`。

**RTX 4070 SUPER 12G 实测**（2026-09-24 本机跑通验证）：

| 测试 | 源 | 帧数 | 输出 | 耗时 | 速度 |
|---|---|---|---|---|---|
| 全片（约 6 秒） | 1280×720 | 143 | 2560×1440 | 586 s | 4.10 s/帧 |
| 片段（2 秒） | 1280×720 | 48 | 2560×1440 | 196 s | 4.08 s/帧 |
| 批量脚本跑同一片段 | 1280×720 | 48 | 2560×1440 | 253 s | 含脚本轮询与搬运开销 |

- 模式 `tiny`，`tiled_vae` / `tiled_dit` 均为默认开启
- 显存峰值约 11.4 GB / 12.3 GB，GPU 利用率 100%
- 帧数、帧率、音轨全部原样保留（143→143、24fps、AAC 立体声）

> **12G 显存必须开分块**：实测关掉 `tiled_dit`（即 `-NoTiledDit`）会直接 OOM——
> 节点申请 19.02 GiB，而 4070 SUPER 上限只有 11.99 GiB。关掉 `tiled_vae`（`-NoTiledVae`）同样 OOM。
> 这两个开关是留给 24G 卡的，12G 卡别动。
>
> 关掉分块后，720p 输入会被切成 18 个 256px 空间块逐个跑（日志里的 `Processing tile n/18`），
> 这是 12G 卡能跑起来的原因，也是它慢的原因。

> **速度参考**：4.1 秒/帧 意味着 1 分钟 24fps 素材（1440 帧）约需 **98 分钟**。
> 这是画质换来的代价——方案一 Video2X 同样 720p 2 倍只要约 0.03 秒/帧（快约 140 倍）。
> 要速度用方案一，要画质用方案二。

**图形界面用法**：跑 `启动ComfyUI.ps1` 打开网页，按第五节"图形界面连线表"拖 4 个节点连起来，
参数按表里填。命令行版本已经把这张图写死在脚本里，所以批量任务不用自己搭。

### 第 4 步：方案三 —— ComfyUI + SeedVR2

```powershell
# 按显卡选档位，只下需要的权重（档位名与批量放大脚本一一对应）
powershell -ExecutionPolicy Bypass -File .\03-SeedVR2\安装SeedVR2.ps1 -Profile 12g   # 4070 Super
powershell -ExecutionPolicy Bypass -File .\03-SeedVR2\安装SeedVR2.ps1 -Profile 16g   # 4070 Ti Super
powershell -ExecutionPolicy Bypass -File .\03-SeedVR2\安装SeedVR2.ps1 -Profile 24g   # 4090
# 显存实在紧张，额外加一份 3B GGUF Q4（约 2.0 GB）
powershell -ExecutionPolicy Bypass -File .\03-SeedVR2\安装SeedVR2.ps1 -Profile 12g -AlsoGguf
```

| 步骤 | 作用 |
|---|---|
| 1 检查环境 | 确认底座就绪；顺带提示 ffmpeg 缺失只影响 10bit 输出 |
| 2 装 SeedVR2 节点 | 克隆官方 ComfyUI 集成节点，并装 `diffusers / peft / rotary_embedding_torch / gguf` 等依赖 |
| 3 下载权重 | VAE 必装；DiT 按档位下载 |
| 4 校验权重 | 核对文件名与体积，避免加载时才报错 |
| 5 自检 CLI | 跑 `inference_cli.py --help`，证明命令行入口依赖齐全 |

档位、权重与体积（体积为 HuggingFace 仓库里的实际文件大小）：

| Profile | 权重 | 体积 | 适用 |
|---|---|---|---|
| `12g` | 3B FP8 + VAE | 约 3.9 GB | 12G 起步档 |
| `16g` | 3B FP16 + 3B FP8 + VAE | 约 10.7 GB | 16G；FP16 画质优于 FP8，FP8 留作备用 |
| `24g` | 7B FP8(mixed) + 7B FP16 + VAE | 约 25.5 GB | 24G；7B FP16 是画质天花板 |
| `all` | 以上全部 + 3B/7B GGUF Q4 | 约 42.4 GB | 三张卡都要用 |

> 体积口径统一为 **1 GB = 10⁹ 字节**（HuggingFace 页面显示的口径）。Windows 资源管理器
> 按 1 GiB = 2³⁰ 字节显示，同一个文件看到的数值会小约 7%，属正常差异。

单个权重文件的准确名称与体积（下错仓库会 404，这里标注了来源仓库）：

| 文件 | 体积 | 仓库 |
|---|---|---|
| `ema_vae_fp16.safetensors` | 0.50 GB | numz/SeedVR2_comfyUI |
| `seedvr2_ema_3b_fp8_e4m3fn.safetensors` | 3.39 GB | numz/SeedVR2_comfyUI |
| `seedvr2_ema_3b_fp16.safetensors` | 6.78 GB | numz/SeedVR2_comfyUI |
| `seedvr2_ema_7b_fp16.safetensors` | 16.48 GB | numz/SeedVR2_comfyUI |
| `seedvr2_ema_7b_fp8_e4m3fn_mixed_block35_fp16.safetensors` | 8.47 GB | **AInVFX/SeedVR2_comfyUI** |
| `seedvr2_ema_3b-Q4_K_M.gguf` | 2.00 GB | AInVFX/SeedVR2_comfyUI |
| `seedvr2_ema_7b-Q4_K_M.gguf` | 4.76 GB | AInVFX/SeedVR2_comfyUI |

> **为什么 7B FP8 要认准 `_mixed_block35_fp16` 这个名字**：节点的 `--dit_model` 只接受
> 「内置注册表里的名字 ∪ 磁盘上已存在的文件」。注册表里的 7B FP8 就是上面这个 mixed 变体
> （它把第 35 号 block 保留 fp16，画质比纯 FP8 好），脚本按注册表名字下，所以装完即可直接跑。
> 注意 `numz` 仓库里另有一个 `seedvr2_ema_7b_fp8_e4m3fn.safetensors`（8.24 GB，纯 FP8），
> 它不在注册表里，但只要你手动放进 `models\SEEDVR2`，同样会被识别成可用模型——不是错误文件。

> 顺带一提，`AInVFX/SeedVR2_comfyUI` 里还有 `seedvr2_ema_3b-Q8_0.gguf`（3.66 GB，介于
> Q4 和 FP8 之间）和 7B 的 `_sharp` 锐化变体，显存卡在中间值时可以手动下载补充。

**批量放大（自带 CLI，最适合挂机）**：

```powershell
# 4070S 挂机跑整个文件夹
powershell -File .\03-SeedVR2\批量放大.ps1 -InputPath "E:\VideoUpscale\input" -Profile 12g

# 4090 冲画质：1080 短边 + 10bit 输出（渐变不易出色带，需 ffmpeg）
powershell -File .\03-SeedVR2\批量放大.ps1 -InputPath "a.mp4" -Profile 24g -Resolution 1080 -TenBit

# 两张卡一起跑一个长视频
powershell -File .\03-SeedVR2\批量放大.ps1 -InputPath "a.mp4" -Profile 24g -CudaDevice "0,1" -ChunkSize 330

# 显存不够时手动兜底
powershell -File .\03-SeedVR2\批量放大.ps1 -InputPath "a.mp4" -Profile custom `
  -DitModel seedvr2_ema_3b-Q4_K_M.gguf -BlocksToSwap 32 -OffloadCpu -BatchSize 5 -TiledVae
```

**关键参数含义**：

| 参数 | 作用 |
|---|---|
| `-Resolution` | 目标**短边**像素（不是放大倍数），脚本自动保持比例 |
| `-BatchSize` | 每批帧数，**要求 4n+1**（1/5/9/13/17/21…）；越大时序越稳、越吃显存。脚本会强制校验 |
| `-BlocksToSwap` | 把 N 层 transformer 换到内存，3B 上限 32、7B 上限 36；**必须配 `-OffloadCpu`** |
| `-ChunkSize` | >0 开启流式分块，长视频不再一次性读进内存 |
| `-TemporalOverlap` | 批与批之间的重叠帧数，用于平滑过渡 |
| `-UniformBatchSize` | 末批补齐，减少结尾闪烁 |
| `-CompileDit` | torch.compile 加速 DiT，首次编译慢，挂机值得开 |
| `-CacheModels` | 批量时模型常驻内存，避免每个文件重新加载；**必须配 `-OffloadCpu`** |
| `-TenBit` | x265 10bit 输出，需 ffmpeg **带 libx265**（脚本会自动探测并注入 PATH，见常见问题第 8 条） |
| `-DitModel` | 必须是 `models\SEEDVR2` 里真实存在的文件名，否则 CLI 会直接拒绝该参数 |

> SeedVR2 是**按目标分辨率放大**，不是按倍数。想 1080p→4K 就把 `-Resolution` 设成 2160。

> **挂机跑之前先知道两件事**：① 目录模式下脚本会先扫一遍输出目录，**全都有了就直接退出**
> （不会白算），要强制重跑加 `-Overwrite`；② 但 CLI 是按「整个目录」调用的，没法只挑几个文件跑，
> 所以**只缺一部分时仍会全量重跑**——想精确续跑，就把已完成的文件先挪出输入目录。

> 上面的批大小和 BlockSwap 层数是**起步值**，不是最优值。显存不够就减小 `-BatchSize`
> 或加大 `-BlocksToSwap`；显存有余就反向调，能提速。

**RTX 4070 SUPER 12G 实测**（`-Profile 12g`：3B FP8 + BlockSwap 24 + VAE 分块，
720p → 1080p，源 48 帧 / 2.0 秒 / 带 AAC 音轨）：

| 阶段 | 耗时 | 说明 |
|---|---|---|
| VAE 编码（10 批 × 5 帧） | 约 31 秒 | 3.1 秒/批，走 tiled 编码（Tile 1024×1024） |
| DiT 扩散（10 批） | 约 40 秒 | 3.9 秒/批，BlockSwap 24/32 层常驻内存 |
| VAE 解码（10 批） | 约 130 秒 | 13 秒/批，是**整条链路最慢的一段** |
| 色彩后处理 + 封装 | 约 8 秒 | LAB 感知色彩迁移 |
| **合计（纯推理）** | **209 秒** | **约 4.4 秒/帧**，脚本端到端 3 分 36 秒 |

启动时显存余量 10.81 GB / 11.99 GB，全程无 OOM。输出校验：
`h264 High` / 1920×1080 / 48 帧（与源一致）/ AAC 音轨 94 帧（与源一致）/ 4.75 MB。

> 换算参考：24fps 素材按 4.4 秒/帧，**10 分钟视频约 17.6 小时**。这印证了对比表里
> "最慢，数小时级"的判断——SeedVR2 是拿来跑关键镜头的，不是拿来批量出全片的。
> 想提速，优先考虑 ① 换 4090 走 `-Profile 24g`（无 BlockSwap，DiT 不换出）；
> ② 关掉 `-TiledVae`（24G 可以关，解码能快不少）；③ `-CompileDit`（挂机跑值得开）。

> 解码比扩散慢三倍多，是因为 VAE 分块 + 逐批走 CPU 往返。12G 上这是必要代价，
> 别为了提速把 `-TiledVae` 关掉——实测直接 OOM。

## 五、图形界面连线表（不想用命令行时）

两条工作流都在 ComfyUI 网页里搭，节点名直接用搜索框找。下面表里写的是**搜索框里能命中的名字**
（节点的英文原名，带不带 🎥🅥🅗🅢 后缀都能搜到）。

### FlashVSR（4 个节点）

| 节点 | 连到哪 | 参数 |
|---|---|---|
| Load Video (Path) | → Video Info 的 `video_info`；→ FlashVSR 的 `frames` | 填视频路径；`frame_load_cap` 设 0 表示全片 |
| Video Info | → Video Combine 的 `frame_rate` | 用它的 `source_fps` 输出（第 1 个输出口），保证输出帧率与原片一致 |
| FlashVSR Ultra-Fast | → Video Combine 的 `images` | `model` 选 FlashVSR-v1.1；`scale` 只能 2/3/4；12G 显存把 `tiled_dit` / `tiled_vae` 打开 |
| Video Combine | 输出节点 | `format` 选 `video/h264-mp4` 或 `video/nvenc_h264-mp4`；`audio` 接 Load Video 的 audio 输出（第 3 个输出口），保留原音轨 |

> Load Video (Path) 的输出口顺序是：1 IMAGE、2 frame_count、3 audio、4 video_info。
> 接线时按这个顺序找，别按名字猜。

> 想细调 `tile_size` / `sparse_ratio` / `kv_ratio` 这些参数，用同一套节点里的
> **FlashVSR Ultra-Fast (Advanced)** + **FlashVSR Init Pipeline** 两个节点组合，
> 普通版把 tile 尺寸、稀疏比例等全部写死成推荐值，只暴露最常用的几个开关。

### SeedVR2（5 个节点）

| 节点 | 连到哪 | 参数 |
|---|---|---|
| Load Video (Path) | → SeedVR2 Video Upscaler 的 `image`；audio 接 Video Combine | 同上 |
| SeedVR2 (Down)Load DiT Model | → Video Upscaler 的 `dit` | 12G：3B FP8 + `blocks_to_swap` 24 + `offload_device` cpu；24G：7B FP8(mixed) + `blocks_to_swap` 0 |
| SeedVR2 (Down)Load VAE Model | → Video Upscaler 的 `vae` | 12G 打开 `encode_tiled` / `decode_tiled` |
| SeedVR2 Video Upscaler | → Video Combine 的 `images` | `resolution` 填短边像素；`batch_size` 要 4n+1；`uniform_batch_size` 建议开 |
| Video Combine | 输出节点 | 同上 |

> 主节点在搜索框里显示为 `SeedVR2 Video Upscaler (v2.5.x)`，版本号后缀会随节点更新变化。
> 实测（本机 ComfyUI 0.37.0 + 节点 v2.5.24）在搜索框里搜 `SeedVR2` 会列出 **9 个**节点——
> 上面用到的 4 个之外，还有 `Conditioning` / `Preprocess` / `PostProcessing` / `TemporalChunk` /
> `TemporalMerge` 这几个进阶节点，本手册的连线不需要它们。

> **12G 卡上别乱改 DiT 模型下拉框**：实测下拉框里列出了注册表里**全部 10 个** DiT 模型，
> 不管文件在不在本地——`SeedVR2 (Down)Load DiT Model` 的 tooltip 也写了 "Models automatically
> download on first use"。默认值就是安装脚本下好的 `seedvr2_ema_3b_fp8_e4m3fn.safetensors`，
> **保持默认即可**。若在 12G 卡上误选 7B 系列，会先自动拉十几 GB 权重，然后在推理时 OOM
> （7B FP16 权重 16.48 GB，远超 11.99 GB 总显存）。

## 六、常见问题

**1. 模型下载卡住 / 失败**
脚本默认走 `hf-mirror.com` 镜像。要换回官方源，先设环境变量再跑：
```powershell
$env:HF_ENDPOINT = "https://huggingface.co"
```
镜像也慢时，用浏览器打开对应仓库页手动下载，再把文件放进 `models\` 下同名目录即可
（文件名必须完全一致，脚本会校验）。注意 7B FP8 的 `_mixed_block35_fp16` 变体和全部 GGUF
在 `AInVFX/SeedVR2_comfyUI`，其余 safetensors 在 `numz/SeedVR2_comfyUI`，别放错仓库下错文件。

**2. 显存不足（OOM）**
优先级从高到低调：① 换更小的模型（7B FP16 → 7B FP8 → 3B FP16 → 3B FP8 → 3B GGUF Q8 → 3B GGUF Q4）；
② 加大 BlockSwap 层数（12G 上 3B 给 24–32，3B 上限 32、7B 上限 36）；
③ 降低 `-Resolution` 或 `-BatchSize`；
④ 打开 VAE 分块。**最后才考虑降分辨率**，因为它直接影响成品质量。

> 档位脚本只自动下 3B 的 Q4_K_M。如果 Q4 画质掉得明显、FP8 又刚好爆显存，
> 可以手动补一份 `seedvr2_ema_3b-Q8_0.gguf`（3.66 GB，同样在 `AInVFX/SeedVR2_comfyUI`），
> 放进 `models\SEEDVR2` 后 `-DitModel seedvr2_ema_3b-Q8_0.gguf` 就能用。

**3. 输出的视频有闪烁 / 抖动**
SeedVR2：加大 `-BatchSize`（时序一致性靠批内帧数）、打开 `-UniformBatchSize`、给 `-TemporalOverlap 3`。
FlashVSR：确认用的是 FlashVSR 而不是逐帧方案；优先用 `tiny` / `tiny-long`，`full` 更吃显存。

**4. 输出没有声音**
FlashVSR 的工作流里 `Video Combine` 的 `audio` 输入必须接上视频的音轨输出，否则默认静音。
SeedVR2 的 CLI **完全不处理音频**——`inference_cli.py` 里没有任何音频参数，输出天然没有音轨。
所以 `批量放大.ps1` 跑完会用 ffmpeg 把源音轨原样接回去（`-c:v copy`，视频流不重编码）。
如果输出仍然没声音，按顺序查：① 源文件本身就没有音轨（正常，脚本会静默跳过）；
② 日志里有没有 `已回接音轨：xxx.mp4` 这行——没有就是 ffmpeg 没找到，见下面第 8 条。

**5. 想对比三套方案的效果**
同一段素材分别用三条命令跑，产物靠文件名后缀区分（**单文件与目录两种模式都会加后缀**）：
`xxx_2x.mp4`（方案一）、`xxx_4x_flashvsr.mp4`（方案二）、`xxx_1080p_seedvr2.mp4`（方案三）。

> SeedVR2 的 CLI 本身是按输入名落盘的（只统一扩展名为 mp4），批量脚本收尾时会统一改名加
> `_<分辨率>p_seedvr2` 后缀——既对齐另外两个方案的命名，也避免「输入目录 == 输出目录」时
> 把源文件覆盖掉。所以**输入目录和输出目录可以设成同一个**，不会误删素材。

**6. 脚本报"未找到 ComfyUI 虚拟环境"**
说明底座还没装或路径变了。先跑 `00-ComfyUI底座\安装ComfyUI.ps1`，
或检查 `common.ps1` 里的 `UPSCALE_ROOT` 是否和你实际安装位置一致。

**7. 安装脚本和批量脚本的 `-Profile` 名字对不上**
现在两边是同一套名字：`12g` / `16g` / `24g`（批量脚本额外有 `custom`）。
装的时候用哪个档位，跑的时候就用哪个档位。

**8. 报错 `Unknown input format: 'rawvideo'` / 输出成了 MPEG-4 Part 2（体积异常大）**
说明 SeedVR2 用的 ffmpeg 是个**精简构建**。`inference_cli.py` 里写死了裸命令 `ffmpeg`
（校验用 `shutil.which("ffmpeg")`，编码用 `subprocess.Popen(['ffmpeg', ...])`），只认 PATH，
所以它会拿到 PATH 上的第一个 ffmpeg —— 有些软件（含 TRAE 自身）自带的 ffmpeg 是
`--disable-everything` 编译的，连 rawvideo 输入格式都没有，也没有 libx265。
本机实测就是这个情况：PATH 第一个是精简版，直接崩。

脚本已处理：`批量放大.ps1` 启动时会自动探测一个**支持 rawvideo 的完整版 ffmpeg**，
把它的目录插到本次进程 PATH 的最前面，子进程就拿到对的那个（日志里会打印 `ffmpeg : <路径>`）。
探测顺序是：环境变量 `FFMPEG_PATH` → PATH → `common.ps1` 里的 `FFMPEG_CANDIDATES`。
都找不到时会直接报错并给出装法，不会闷头跑出个坏文件。

要自己指定，二选一：
```powershell
# 临时（当前窗口有效）
$env:FFMPEG_PATH = "D:\tools\ffmpeg\bin\ffmpeg.exe"

# 或永久：winget install Gyan.FFmpeg，装完重开终端
```

> 判断手上这个 ffmpeg 够不够用，一条命令就能验：
> `ffmpeg -hide_banner -demuxers | Select-String rawvideo` —— 有输出才算可用。
> 顺便看下 `ffmpeg -hide_banner -encoders | Select-String libx265`，有输出才支持 `-TenBit`。

**9. 只想知道"输出到底对不对"**
`批量放大.ps1` 只保证"跑完了"，不保证"画面正常"。想核对，用 ffprobe 看三件事：
```powershell
ffprobe -v error -show_entries stream=codec_name,width,height,nb_frames -of default=noprint_wrappers=1 "输出.mp4"
```
① 视频 `codec_name` 应该是 `h264`（若是 `mpeg4` 就是踩了上面第 8 条）；
② `width/height` 是否达到目标分辨率；③ `nb_frames` 是否与源一致（少了说明有丢帧）。
音轨则看有没有 `codec_name=aac` 那一行。

### 本轮实测确认的数据（RTX 4070 SUPER 12G）

- `-Profile 12g`（3B FP8 + BlockSwap 24 + VAE 分块）跑 720p→1080p、48 帧：
  纯推理 209 秒（约 **4.4 秒/帧**），脚本端到端 3 分 36 秒，全程无 OOM。
- 耗时分布：VAE 编码 31 秒 / DiT 扩散 40 秒 / **VAE 解码 130 秒** / 后处理封装 8 秒。
  **解码是最慢的一段**（VAE 分块 + 逐批 CPU 往返），与"扩散模型慢在扩散"的直觉相反。
- 输出完整性：`h264 High` / 1920×1080 / 48 帧（与源一致）/ AAC 94 帧（与源一致）。
- 据此换算 24fps 素材约 17.6 小时/10 分钟片，印证对比表"数小时级"的定位。
- 图形界面通路也已实测：ComfyUI 0.37.0 冷启动时 `seedvr2_videoupscaler` 导入耗时 **1.9 秒**、
  无报错，9 个节点全部出现在 `/object_info` 里；DiT 默认值 = 已下载的 3B FP8，VAE 下拉只有 1 项。
- 启动日志里的两条环境信息（本机实测，非推测）：`SeedVR2 optimizations check:
  SageAttention ❌ | Flash Attention ❌ | Triton ✅`（可选加速包未装，不影响出片）；
  `Conv3d workaround active: PyTorch 2.14.0, cuDNN 92400 (fixing VAE 3x memory bug)`
  （节点自带针对 3D 卷积显存膨胀的补丁，12G 上跑得动 VAE 分块与此有关）。
- 冷启动后空闲显存 `10.75 GB free / 11.99 GB total`，与推理时的启动余量一致。
